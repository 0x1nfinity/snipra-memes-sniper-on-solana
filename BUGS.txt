Z. CRITICAL — 2026-08-01
============================================================

✅ [USER] BUG-Z1: Posisi sudah ditutup (base token diswap ke SOL) tapi bot
   masih mengatakan posisi terbuka & tracking posisi. Dua masalah:
   (1) close position stale, (2) PnL ticker tidak bekerja dengan baik.

   ROOT CAUSE #1 — Close position stale:
   SolanaChain.sell() dan EvmChain.sell() menghitung receivedNative dari
   query saldo RPC SETELAH swap sukses. Jika RPC gagal (timeout/rate-limit)
   SETELAH tx on-chain sudah confirmed, sell() throw → closePosition()
   tidak pernah dipanggil → posisi tetap di state.open selamanya.

   Fix (solana.js:180-209, evm.js:198-238):
   - solBefore / ethBefore query dibungkus try-catch (best-effort)
   - solAfter / ethAfter query dibungkus try-catch DENGAN fallback ke
     quote outAmount jika gagal
   - Swap SUDAH SUKSES → JANGAN PERNAH THROW setelah titik ini
   - Log warning + pakai quote sebagai estimasi receivedNative

   ROOT CAUSE #2 — PnL ticker:
   _refreshPrices() tidak ada retry logic. DexScreener API transient error
   menyebabkan seluruh chain skip price update, posisi tampil stale.
   Tidak ada mekanisme deteksi harga stale (token delisted/rug).

   Fix (manager.js:66-125):
   - Retry 1x dengan delay 2s jika tokensBatch() gagal
   - Deteksi harga stale: jika lastPriceAt > stalePriceWarnSec, log warning
   - Config baru: monitor.stalePriceWarnSec (default 600s)

   DEFENSE-IN-DEPTH (manager.js:133-153):
   - Safety net di awal _applyRules(): cek on-chain token balance.
     Jika balance = 0 tapi posisi masih di state.open → auto-close.
   - Menangani posisi yg sudah terlanjur stuck dari bug versi lama.

   File yang dimodifikasi:
     src/chains/solana.js    — try-catch post-swap balance query
     src/chains/evm.js       — try-catch post-swap balance query
     src/positions/manager.js — retry DexScreener, stale detect, safety net
     src/config.js           — monitor.stalePriceWarnSec

G. RECHECK — 2026-08-01 (audit ulang klaim FIXED di atas)
============================================================

User melaporkan BUG-Z1 TERULANG (posisi close on-chain, bot masih anggap
terbuka) meski sudah ditandai FIXED. Audit ulang seluruh working tree
(bukan cuma percaya changelog) menemukan gap nyata:

✅ [RECHECK] BUG-Z1 lanjutan — root cause ASLI belum tersentuh:
   Fix 519c901 hanya membungkus query SALDO (solBefore/solAfter) dgn
   try-catch. Yang TIDAK dibungkus: loop konfirmasi swap itu sendiri —
   solana.js _confirm() memanggil getSignatureStatuses() tanpa try-catch
   di dalam loop polling 2s x 30 — jika RPC error sekali saja di tengah
   polling (rate-limit/network blip, cukup umum dalam window 60s), _confirm
   throw walau swap SUDAH sukses on-chain → sell() throw → closePosition()
   tidak pernah dipanggil. evm.js punya celah setara: tx.wait() bisa throw
   krn provider error transient walau tx sudah mined.
   Fix nyata: _confirm() bungkus getSignatureStatuses per-iterasi (retry,
   jangan throw kecuali s.err asli). evm.js: tx.wait() fallback ke poll
   manual getTransactionReceipt() sebelum benar2 throw.
   Defense-in-depth JUGA diperbaiki: safety net dulu cuma jalan sekali saat
   startup (hemat RPC) — sekarang jalan berkala tiap tick, dibatasi
   monitor.onchainReconcileSec (default 60s), supaya posisi yg closed
   di luar tracking bot terdeteksi dalam ~1 menit saat bot berjalan,
   bukan cuma saat restart.

⚠️ [RECHECK] BUG-B4 — TIDAK sepenuhnya fixed:
   cfg.activeChain masih dibaca di telegram/commands/config.js
   menuKeyboard() (checkmark tombol chain) padahal field ini sudah
   dihapus dari DEFAULTS — selalu undefined/false, checkmark tidak pernah
   nyala. handleMenuCallback juga masih menulis setPath('activeChain', arg)
   — key mati yang tidak dibaca apa pun. Dibereskan sekalian saat
   pemisahan chain robinhood (menu chain-picker robinhood dihapus total).

⚠️ [RECHECK] BUG-B5 — race condition pada rate limiter:
   _rateLimit() di dexscreener.js membaca _lastCall[key] lalu BARU update
   setelah sleep() selesai — mapLimit(4 worker konkuren) bisa baca nilai
   basi yang sama dan tembak bareng, melebihi rate yang dimaksud.
   Fix: reservasi slot (_lastCall[key] = next) SYNCHRONOUS sebelum await
   sleep, supaya tiap caller konkuren antre berurutan.

⚠️ [RECHECK] BUG-F1 — fix sebelumnya salah sasaran:
   persistNow() diklaim diperbaiki tapi fungsi itu sepenuhnya sinkron —
   tidak pernah ada race di situ. Bug nyata ada di persist() (debounced):
   nama file target sudah benar (capture modeAtCall), tapi KONTEN yang
   ditulis diambil dari variabel `state` module-level saat timer 500ms itu
   FIRE, bukan snapshot saat persist() dipanggil. loadState() (dipanggil
   saat /mode ganti) mereset `state` tanpa flush timer pending dulu — jadi
   switch mode cepat saat debounce masih ngantri bisa nulis KONTEN mode
   baru ke FILE mode lama. Fix: loadState() sekarang panggil persistNow()
   (flush thd mode & state LAMA) sebelum reassign ke mode baru.
